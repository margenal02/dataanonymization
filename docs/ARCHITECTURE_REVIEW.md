# 产品、数据与技术架构审查报告

## 1. 审查结论

本系统已经具备“本地文件处理、候选识别、人工复核、可逆脱敏、训练样本沉淀”的完整业务闭环，适合在受控内网开展试运行。本轮审查重点不是继续堆叠规则，而是让识别质量可度量、训练数据可直接使用、大文件处理可控、错误可追踪、界面信息层级更清楚。

上线边界保持不变：系统按需求不登录，因此不能直接暴露到互联网；自动识别不能代替人工复核；PDF 属于内容重建而不是原版式编辑；UIE-base 的训练数据沉淀不等于模型权重已经更新。

## 2. 本轮已实施优化

| 视角 | 发现 | 优化结果 |
|---|---|---|
| 数据分析 | 原统计只显示任务数和实体总数，无法判断识别效果 | 新增质量洞察：候选采纳率、人工否决、人工补漏、类别修正、同实体合并、类别/格式分布、任务完成率和识别耗时 |
| 模型数据 | 导出训练集的提示词与线上 UIE 查询提示词不一致 | 建立共享实体契约；训练使用“单位名称、烟草品牌或产品名称、烟叶产区”等线上同口径提示词，并导出人工复核后的负样本 |
| 后端性能 | 候选重叠检测用 Python 整数集合，长文本占用内存高；逐实体 `replace` 会反复扫描全文 | 重叠检测改为紧凑字节位图；脱敏和恢复改为最长优先的单次正则扫描；复核出现位置改为一次索引 |
| 后端可靠性 | 健康检查只返回固定成功；通用异常提示查看日志但没有统一记录 | 健康检查增加数据库查询；任务、训练预标、复核重处理和恢复异常写入容器错误日志，并只记录任务 UUID，不记录敏感原文 |
| 资源安全 | 通用 API 限流不能单独保护 OCR/UIE 重任务 | 文件处理类写请求增加每来源每小时 60 次独立限流；读取和进度轮询不占用此额度 |
| 前端架构 | 全文预览逻辑在脱敏复核和训练标注中重复，单页状态和模板过于集中 | 抽出复用的 `DocumentPreview` 和独立 `AnalyticsPanel`；预览实体索引只计算一次 |
| 前端体验 | 候选较多时难以定位；非上传页面的错误不可见 | 候选支持字段/匿名代码搜索、类别筛选和全文出现次数；错误改为全局可关闭提示；训练上传也执行前置大小校验 |
| 可访问性 | 部分日期异常可能让页面渲染失败，错误提示缺少全局操作 | 日期格式化增加非法值保护；错误区使用 `role=alert`，所有图标按钮保留标题或辅助标签 |

## 3. 当前数据闭环

```text
业务文件
  -> 规则 / 加密本地词库 / UIE-base 候选
  -> 全文统一高亮 + 出现次数 + 同实体建议
  -> 人工采纳 / 否决 / 改类 / 补漏 / 合并
  -> 脱敏文件与可逆加密映射
  -> 精确词库立即生效
  -> 加密训练样本
  -> 流式导出 UIE JSONL
  -> 独立划分训练集、验证集并集中微调
```

“质量洞察”的候选采纳率用于观察精确度趋势，人工补漏量用于观察召回短板。它们没有独立金标准集，因此不能写成正式的 Precision、Recall 或 F1。正式模型验收应维护不参与训练的金标准文档集，至少按单位、人名、产品、产区、地址五类分别计算字符区间级 Precision / Recall / F1，并单列 OCR 字符错误率。

## 4. 指标口径

- **机器候选**：进入某次人工复核界面的唯一字段数。
- **候选出现位置**：候选字段在文件名和全文中的全部精确出现次数。
- **候选采纳率**：人工保留候选数 / 机器候选数；只用于趋势观察。
- **人工补漏**：复核人员主动补录、且不属于候选改类的字段数。
- **类别修正**：保留字段但修改敏感类型的数量。
- **同实体合并**：人工确认共用匿名代码的全称/简称组数。
- **识别耗时**：首次从文件结构检查开始，到候选预览和映射生成完成的服务端耗时，不包含人工等待时间。

分析 API 只返回聚合计数和耗时，不返回人名、单位、地址或原文。训练文档与任务映射仍然加密保存。

## 5. 架构边界与后续路线

### P0：试运行前

1. 用本单位真实但受控的脱敏测试集建立金标准，覆盖扫描 PDF、复杂 DOCX 表格、OFD 和常见简称。
2. 通过防火墙只放行可信终端；跨主机访问时配置 HTTPS。启用 HTTPS 反向代理后设置 `DJANGO_HTTPS=1`。
3. 配置 Docker CPU/内存限制并执行 1、2、3 个并发扫描 PDF 的压力测试，确定本机安全并发数。
4. 备份 MySQL、`media_data` 和 `MAPPING_ENCRYPTION_KEY`，并做一次真实恢复演练。

### P1：规模化使用

1. 将同步 OCR/UIE 任务迁移到独立作业队列。建议 Redis + Celery，Web 请求只创建任务，Worker 执行 OCR、识别和文档重建；增加取消、重试、超时和幂等键。当前同步方案适合单机低并发，不能假设浏览器断线后任务一定可控。
2. 将 `views.py` 继续拆分为任务、复核、训练和分析模块，并把文件处理编排下沉到 service 层；为 API 增加 OpenAPI 契约测试。
3. 训练集增加版本、审核人、数据集快照、训练/验证划分和模型版本登记，形成可回滚的模型注册表。
4. 即使业务页面不登录，也建议在上层网关接入单位统一身份认证，并为删除、训练集导出和正式文件下载增加审计身份。

### P2：模型能力

1. 在积累足够人工样本后微调 UIE-base，同时保留规则与精确词库作为高确定性通道。
2. 建立简称候选的可解释特征和组织主数据字典；相同实体判断继续由人工确认，不允许模型静默合并。
3. 若硬件允许，可评估小型本地大模型作为“候选召回器”，但输出只能进入人工复核，不能直接改写文件；需要用同一金标准集比较召回增益、误报、时延和内存，而不是只比较模型参数量。

## 6. 验收基线

- Django 系统检查通过。
- 后端自动化测试全部通过，覆盖格式处理、人工复核、训练标注、质量指标、数据库健康检查和安全校验。
- Vue 生产构建通过。
- Python 依赖一致性检查通过。
- Bandit 静态安全扫描无发现。
- npm 官方生产依赖审计为 0 个已知漏洞。
- 本轮改动必须在本地浏览器完成数据处理台、质量洞察、训练标注和移动端断点的视觉验收。

以上结论是当前代码与本地测试环境的工程审查，不替代第三方渗透测试、等保测评、密码应用测评或真实生产压力测试。
